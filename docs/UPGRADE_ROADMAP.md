## Purpose, authority, and working agreement

This tracker consolidates the independent Architecture, Backend, Frontend, and QA/security audits. `AGENTS.md` remains the source of repository development rules. The Lead Engineer owns prioritisation, coordination, integration, review, and honest reporting of verification.

The client has authorised preparation of this roadmap and supplied two clinical decisions below. Substantial implementation must wait for roadmap approval. Approval authorises only the development scope stated in the client's reply; it never authorises merging, deployment, production-data changes, credential rotation, Git-history rewriting, or production-setting changes. Continue through approved items without asking about routine technical choices; stop only for material product, compatibility, cost, or scope decisions.

Use dedicated branches and reviewable pull requests. For significant changes, use a reviewer who did not implement the change. Do not assign concurrent edits to shared files. Prefer targeted repairs and small extractions over broad rewrites. No new queue, paid service, frontend framework, database framework, or major dependency upgrade is assumed.

## Recommended order and expected benefit

Priority means P1 = immediate correctness/security or release-readiness concern; P2 = next reliability/usability/operating improvement; P3 = maintainability after behaviour is protected. Packaging is a blocker **before another image build**. Production exposure, workload, and the validity of tracked credentials have not been assessed.

Complexity is relative: S = local repair; M = several collaborating paths; L = cross-layer workflow or compatibility/migration work. These are not elapsed-time or cost promises. Refine estimates after the Understand step for each item.

## Required process and completion evidence

For every approved item:

1. **Understand:** inspect current code/callers and reproduce or characterise the behaviour with synthetic data. Record affected modules and risks before editing.
2. **Consult:** use the decision register for material behaviour, workflow, compatibility or cost choices. Explain the recommendation, meaningful alternatives and consequences in plain language. Do not re-ask confirmed decisions or routine technical choices.
3. **Design and assign:** define contracts and file ownership, tests and rollback. Delegate independent work only; record important architecture decisions without adding unnecessary process/dependencies.
4. **Implement:** make targeted changes on a dedicated branch, preserve unrelated working functionality and never modify production data or expose secrets.
5. **Verify:** add meaningful regressions; run relevant tests/checks/build-only validation in an isolated environment. Investigate failures and resolve them or leave the item explicitly blocked. Compare old/new behaviour where practical. Record exact commands, environment, results and unverified limits.
6. **Review:** a separate reviewer checks significant logic, regressions, security, performance, maintainability and approved requirements. Resolve material findings before declaring readiness.
7. **Report and prepare release:** describe what improved, user-visible changes, verification, limitations, readiness and next item. Prepare the PR and update this tracker. Do not merge/deploy without explicit approval.
8. **Continue or hand over:** proceed with the next approved unblocked item. If a decision/session boundary prevents progress, record the exact state, branch/PR, remaining checks and next action so another session can resume.

Release gates are proportional to the change: relevant Python 3.11 tests; disposable PostgreSQL for SQL/schema/concurrency work; browser evidence for UI/security flows; safe image-context/build inspection for packaging; measured workload evidence for performance claims. Always inspect the complete diff and run `git diff --check`. Keep DB/log/bytecode/environment artifacts out of changes.

Rollback is item-specific: code-only fixes should be small and reversible; schema/identity changes need additive compatibility and tested recovery; security configuration changes need a safe configuration path and session-impact plan; job changes must address in-flight work. Never restore a known insecure default or sensitive image context as a recovery shortcut. Approval of development does not authorise a production rollback operation.
